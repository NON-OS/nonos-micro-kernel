# The AIR

The step AIR is the object that turns "the VM ran" into "the constraints hold." It
is in `userland/nonos_zkolang/src/air.rs`. A reviewer who reads this page and that
file can see that the trace is a fixed-width algebraic matrix and that the verifier
rebuilds the whole constraint system from the public program and the public
values, holding nothing back.

## The trace is a matrix

The trace is a matrix with `TRACE_WIDTH = 35` columns and a power-of-two number of
rows, one row per executed step, padded with halt rows. The width is `RF_BASE + REGS`,
that is 19 step columns and 16 register-file columns. The columns are:

```
  0        CLK           the step counter, rising by one
  1..12    selectors     S_IMM S_ADD S_SUB S_MUL S_INV S_EQ S_SEL
                         S_BOOL S_ASSERT S_INP S_OUT S_HALT (one-hot)
  13..15   A B C         the three operand values a row reads
  16       D             the result the row writes
  17       IMM           an immediate (literals and inputs)
  18       AUX           a witness (the inverse for Inv and Eq)
  19..34   register file the 16 registers, holding state before the row
```

The window the transition sees is two rows, row k and row k+1 (`WINDOW = 2`), so a
constraint can compare a register before and after a write and can check the clock
advances.

## The transition constraints

There are 46 transition constraints (`NUM_TRANSITION = 27 + 3 + REGS`), each a
polynomial of degree at most three (`DEGREE = 3`). They fall into groups. The
prose here matches the `transition_impl` function in `src/air.rs`; read them
together.

Selector well-formedness. Each of the twelve selectors is a bit (`s * (s - 1) = 0`),
and they sum to one, so every row names exactly one opcode.

Arithmetic. Gated by the row's selector, the result column equals the operation:
add is `s_add * (d - (a + b))`, and multiply, subtract, and the immediate load are
the same shape. Inverse is witnessed: `s_inv * (a * aux - 1)` forces `aux` to be
`a^{-1}` (which also forces `a` nonzero), and `s_inv * (d - aux)` sets the result.
Equality decides a clean bit from the difference `a - b` and its inverse witness:
if they differ, `d * diff = 0` forces the bit to zero and `d + diff * aux - 1 = 0`
forces `aux` to be the inverse; if they are equal, the bit is one. Select checks
`c` is a bit and computes `c ? a : b` as `c*a + b - c*b`. The two constraint
opcodes assert a bit (`s_bool * (a * (a - 1))`) or a zero (`s_assert * a`). Input
loads the immediate (`s_inp * (d - imm)`), whose value the boundary pins to the
public input.

Ordering. The clock rises by one: `next_clk - clk - 1 = 0`.

Register binding. This is the group that makes the proof mean a program ran rather
than that a bag of individually valid rows exists, and it is worth stating how it
works, because it is where zKølang differs from a general zkVM.

## Register binding as a public circuit

zKølang names registers by compile-time index. `Add { d, a, b }` reads registers `a`
and `b` and writes `d`, and those indices are fixed in the program text, not
computed at runtime. So the data flow, which row's result feeds which row's
operand, is a public property of the program, known to the verifier.

The AIR carries that data flow as periodic columns: for each row, a one-hot vector
saying which register it writes, and three one-hot vectors saying which registers
its three read ports name (`NUM_PERIODIC = 4 * REGS = 64` periodic columns,
generated by `periodic_columns` in `src/air.rs`). The register file is threaded
through the trace in columns 19 to 34. A read is then a linear combination

```
  operand = sum over k of (read_onehot_k * regfile_k)
```

and a write is

```
  regfile_next_k = (1 - write_onehot_k) * regfile_k + write_onehot_k * result
```

Both are linear in the trace, because the one-hot coefficients are public
constants, not witness values. Register binding therefore adds no constraint
degree and no soundness assumption: the wiring is recomputed by the verifier from
the public program, so a prover cannot lie about which register an operand came
from. This is a different construction from the grand-product permutation a zkVM
uses for a random-access register file, and it is available precisely because
zKølang's register indices are static. A grand-product permutation would be needed
only for a dynamic memory, which a future memory extension would add.

## The boundary constraints

The boundary pins specific cells (`boundary` in `src/air.rs`): the clock starts at
zero, the final row is a clean halt, and every register starts at zero. On top of
that fixed set, the public bindings are added: for each `Inp` row, the immediate
column is pinned to the committed public input, and for each `Out` row, the operand
column is pinned to the committed public output. Because the verifier constructs
the same AIR from the same public program and public values, these bindings are
part of the checked statement. A prover who used a different input, or claimed a
different output, produces a trace whose pinned cells do not match, and the proof
is rejected.

## Binding to the STARK

The AIR implements the `Air` and `AirExt` traits of `nonos-stark`, so the transition
is written once over a field abstraction and evaluated over both the base field
and its quadratic extension. The trace matrix and the boundary are handed to the
money-grade Poseidon-committed prover (`stark_prove_poseidon_ext`), which produces
a transparent STARK. This document does not re-derive that prover; see the NØNOS
verification paper for the STARK itself. What matters here is the seam: zKølang
produces a standard AIR instance over the shared field, and the STARK does the
rest.

## Completeness of the AIR

Every opcode the machine has is constrained here; the AIR proves whole programs
with no unenforced instruction. A random-access memory is not part of this
language. Were one added, its consistency would be a permutation argument over
sorted accesses, a separate and larger construction; that is a future major
version and nothing above depends on it.
